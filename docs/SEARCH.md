# Architecture & hyperparameter search

`search/run_search.py` + `search/report.py` answer the "which architecture
and settings work best" question in one pass: describe the space you want
to explore in a YAML file, run it (locally or on a cluster), and get back a
ranked table + comparison plots.

## Quick start

```bash
cd src
python search/run_search.py --config pipeline/config_search_example.yaml --dry-run   # see the plan
python search/run_search.py --config pipeline/config_search_example.yaml             # actually train
python search/report.py --search-dir /path/to/experiments/search_arch_search_v1
```

Open `search_arch_search_v1/report.md` (and `plots/*.png`) for the results.

## What gets swept

Copy `pipeline/config_search_example.yaml` and edit:

- **`search:`** — shared settings: data source, output target, scale,
  epochs, early stopping, train/val split, `strategy` (`grid` = full
  Cartesian product, `random` = sample `n_samples` combinations — use this
  when the full grid is too large to run in the time available), and
  whether to log every run to MLflow (`use_mlflow`).
- **`architectures:`** — one block per architecture, each with its own
  grid over `layers` (depth), `neurons` (width), `activation`, `dropout`,
  `batchnorm`, `loss`, `optimizer`, `lr`, `scheduler`, and `seeds` (repeat
  the same config with different seeds for a robustness check). Currently
  implemented: `mlp` (any `input_type`) and `cnn` (`input_type: grid`
  only, since a CNN needs the spatial grid representation — see
  `models/cnn.py`). Add a block for any other architecture name and it
  will be printed and skipped rather than crash, so the YAML can already
  describe the search you *want* even before e.g. `models/kan.py` exists;
  it starts running automatically once that architecture is implemented
  and added to `search.space.IMPLEMENTED_ARCHITECTURES`.

Every hyperparameter combination is trained and evaluated independently;
all combinations for a given `input_type` share the same train/val/test
split (fixed via `search.seed_split`), so comparisons are apples-to-apples.

## Output layout

```
<search.path>/search_<id>/
├── config_resolved.yaml     # exact config used (for reproducibility)
├── results.csv              # one row per run: full hyperparams + test metrics
├── results_shard_<i>.csv    # instead of results.csv, if run with --shard-count > 1
├── report.md                # generated by search/report.py
├── ranked_results.csv       # results.csv sorted by the chosen metric
├── plots/
│   ├── architecture_comparison.png
│   ├── metric_vs_neurons.png       # width sensitivity
│   ├── metric_vs_layers.png        # depth sensitivity
│   └── best_model_pred_vs_true.png
└── runs/
    └── run_<n>_<architecture>_<input_type>/
        ├── best_model.pth, history.json, metrics.json, plots/   (Trainer output)
        ├── predictions.npz                                       (for report.py)
        └── error.txt                                              (only if the run failed)
```

`results.csv` is flushed after every single run, so a search that gets
killed partway through a long job still leaves usable, reportable results
for everything trained up to that point.

## Choosing the ranking metric

`search/report.py --metric <name>` (default `resolution`, the std. dev. of
`pred - true`, a common physics figure of merit for shower reconstruction).
Any column in `results.csv` works, with the correct "better direction"
already known for: `mse`, `mae`, `rmse`, `relative_error` (lower is
better), `r2`, `correlation` (higher is better), `bias` (closest to 0),
`energy_scale` (closest to 1).

## Running on a cluster

`scripts/slurm_search.sh` shards the full grid across a SLURM job array
(`--shard-index`/`--shard-count`), so N array tasks train in parallel;
run `search/report.py` once after they all finish — it automatically
merges every `results_shard_*.csv` it finds. See
`docs/INSTALL_SERVER.md` for the rest of the server setup (venv/Docker,
MLflow tracking URI).

## Large files (millions of showers) {#large-files}

`search.dat_file`/`data_path` load the *entire* particle table into memory
via `corsario.open()`/`particles_csv()`. That does not scale to a file
with millions of showers (see `corsario`'s `docs/LARGE_FILES.md` for the
memory math) -- for that scale, build compact per-shower features **once**
with `data/build_feature_dataset.py`, then point the search at the result:

```bash
cd src
python data/build_feature_dataset.py \
    --dat-file /data/DAT_15M \
    --out-dir /data/features/run1 \
    --input-types stats grid \
    --batch-size 50000
```

This streams the file in batches (never holding more than one batch's
particles in memory), computes features per batch with the exact same
`data.features.{stats,grid,circle}` functions the small-scale path uses,
and writes `<out-dir>/{stats,grid}.h5` incrementally. **It is resumable**:
the HDF5 file's current row count is the checkpoint, so re-running the
same command after an interruption (killed job, time limit, crash) picks
up where it left off instead of starting over — verified to produce a
byte-identical result to an uninterrupted run either way (`tests/`).

Then in the search YAML, replace `dat_file`/`data_path` with:

```yaml
search:
  feature_dir: "/data/features/run1"
  # dat_file / data_path no longer needed -- run_search.py loads the
  # prebuilt stats.h5 / grid.h5 directly and never touches the raw file.
```

`run_search.py` loads each `<input_type>.h5` once (cached, same as the
small-scale path) and reuses it across every hyperparameter combination
that needs it. This is also what makes iterating on a search *fast* at
this scale: the multi-hour/day file scan happens exactly once in
`build_feature_dataset.py`, and every subsequent `run_search.py` run (a
different hyperparameter grid, a different loss, whatever you want to
try next) reads a few-GB HDF5 file instead of re-scanning the raw file.

CNN training also works from the prebuilt `grid.h5` — `run_search.py`
reshapes the stored flattened grid back into the channel-first tensor
Conv2d needs (an exact reshape/permute of the same values, not a
recomputation) — so `build_feature_dataset.py` only needs to build `grid`
once for both the MLP and CNN architectures to use it.

### A note on the grid's spatial range

`grid_generator`'s spatial bins must span a **fixed** x/y range shared by
every batch — computing it separately per batch (what happens if you call
`grid_generator` batch-by-batch without a fixed range) would make each
batch's "cell (0,0)" cover a different physical region, silently
corrupting the feature. `build_feature_dataset.py` handles this by
default: it samples the first `--range-sample-showers` showers (500,000 by
default) to estimate a global x/y range before building `grid.h5`. Pass
`--x-range MIN MAX --y-range MIN MAX` explicitly instead if you know your
detector array's physical footprint (preferred if your file might be
sorted in a way that correlates shower size with file position, e.g. by
ascending primary energy — a sample of the *front* of such a file would
not be representative), or `--range-sample-showers 0` to scan the whole
file for the exact global min/max instead of a sample.

### Estimating runtime before committing to a full run

`build_feature_dataset.py` prints a running showers/sec rate as it goes.
Run it once with a small `--batch-size` on a *copy of just the first
portion* of your file (or let it run for a few minutes and Ctrl-C — it's
resumable, so no work is lost) to get a realistic rate for your data and
hardware, then extrapolate: at, say, 2,000 showers/sec, 15,000,000 showers
is ~2 hours; at 500 showers/sec (larger/thinned showers, CPU-bound), the
same file is ~8 hours. `--device cuda` moves the per-shower feature
aggregation (all torch `scatter_add` operations) onto a GPU if available,
which is worth trying for large runs since it does not require any other
changes. `scripts/slurm_build_features.sh` submits this as its own SLURM
job (separate from `slurm_search.sh`, since it only needs to run once and
should typically get a longer time limit and its own checkpoint-friendly
retry logic).

## Avoiding a factorial explosion {#optuna}

A `grid` strategy with, say, 3 `layers` x 3 `neurons` x 2 `activation` x 2
`dropout` x 3 `loss` x 3 `seeds` x 3 `input_types` is already 486 MLP runs
— multiply by `epochs` and your dataset size to estimate wall-clock time
before submitting (`--dry-run` prints the exact count). Adding more
dimensions (more losses, an optimizer sweep, a learning-rate sweep, a
second architecture) multiplies further — this grows combinatorially by
construction, so at some point exhaustive grid search stops being
practical no matter how much compute you have. Three ways to handle that,
in increasing order of sophistication:

1. **`strategy: random`** with a modest `n_samples` (e.g. 30-50): samples
   uniformly from the same space instead of enumerating it. Bergstra &
   Bengio (2012) showed this is often close to as good as grid search for
   a given budget, since not every hyperparameter matters equally, and
   grid search "wastes" combinations varying unimportant ones. Cheap to
   try, no new dependency, but it doesn't learn from earlier trials.

2. **`strategy: optuna`**: Bayesian optimization (TPE) over the *same*
   discrete choices — each trial is chosen based on what worked well in
   previous trials, not blindly. Combined with **pruning** (killing a
   trial partway through if its validation loss is clearly worse than
   other trials at the same epoch, via `optuna.pruners.MedianPruner`),
   this is the most compute-efficient option when each individual training
   run is expensive (e.g. your large feature datasets) — bad
   configurations get cut off after a few epochs instead of running to
   completion. See `pipeline/config_search_optuna_example.yaml`; the
   `architectures:` block uses the exact same schema as `grid`/`random`,
   just interpreted as "choose from these options" rather than "try all
   combinations of these options":

   ```yaml
   search:
     strategy: optuna
     optuna:
       n_trials: 50
       objective_metric: resolution
       pruning: {enabled: true, n_warmup_steps: 5}
   ```

   Requires `pip install -e ".[optuna]"`. Run exactly like the other
   strategies (`python search/run_search.py --config ...`); `report.py`
   works unchanged (pruned trials show up as `status=pruned`, excluded
   from ranking but counted in the summary).

   **Parallel workers, one shared study**: unlike grid sharding (which
   splits a fixed list), Optuna trials are sequential by nature (each one
   can use every previous trial's result) — but multiple processes *can*
   collaborate on one study via shared storage:

   ```yaml
   optuna:
     storage: "sqlite:////path/to/experiments/my_study.db"   # 4 slashes = absolute path
     study_name: "my_study"
   ```

   Then run several `run_search.py` processes (e.g. `scripts/slurm_search_optuna.sh`,
   a SLURM job array) with different `--shard-index`/`--shard-count` —
   this only affects output file/run-directory naming so workers don't
   collide; every worker reads and writes the *same* study, so trial N+1
   on worker B benefits from trial N finishing on worker A. Verified
   (`tests/`) to not collide on run directories or results files, and that
   a second worker does see and build on the first worker's trials.

3. **Narrow, then widen**: run a cheap random or Optuna search first (few
   epochs, small `n_trials`) to find which architecture/input_type/loss
   region is promising, then write a focused `grid` config around just
   that region for a final, exhaustive, publication-grade sweep of the few
   dimensions that turned out to matter (e.g. just width and depth, once
   architecture/loss/optimizer are fixed).
